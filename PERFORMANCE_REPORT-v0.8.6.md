# Отчёт по пакетной классификации — v0.8.6

## Цель изменения

Сократить количество HTTP-запросов к DeepSeek при обработке потока писем и повысить агрегатную пропускную способность, не направляя дополнительные обычные письма на FAST-путь ради искусственного снижения AI-нагрузки.

## Новая пакетная схема

1. SMTP Gateway сохраняет каждое письмо в прежнюю durable queue.
2. Worker забирает первое доступное задание и собирает до 20 заданий очереди.
3. После первого задания он ждёт пополнения пакета не более 250 мс, проверяя очередь короткими интервалами.
4. Для каждого письма выполняются прежние parsing и Risk Engine.
5. Письма, которые Risk Engine разрешил пропустить мимо AI, обрабатываются по прежнему FAST-пути.
6. Только письма с `requires_ai=true` объединяются в запросы DeepSeek максимум по 10 писем.
7. Ответ модели должен содержать один результат на каждый числовой ID. Код сопоставляет результаты по ID, проверяет схему и повторно запрашивает индивидуально только отсутствующие/некорректные результаты.
8. Если пакетный API-запрос полностью недоступен, для его писем применяется существующий локальный fallback без серии дополнительных сетевых запросов по одному на каждое письмо.
9. Если локальные сильные сигналы противоречат ответу BENIGN, сохранена существующая индивидуальная перепроверка.
10. Оригинальная доставка, доставка alert, retries и per-recipient state не объединяются и не меняются.

## Настройки

```env
QUEUE_BATCH_MAX_MESSAGES=20
QUEUE_BATCH_WAIT_SECONDS=0.25
DEEPSEEK_BATCH_SIZE=10
```

250 мс выбраны намеренно: ожидание в несколько секунд снизило бы задержку только в случае появления большого пакета, но явно ухудшило бы задержку редких/единичных писем. При высокой интенсивности worker завершает сбор раньше лимита, как только набирает 20 заданий.

## Верифицированные проверки в этой среде

- `python -m pytest -q`: **84 passed**.
- `python scripts/run_p0_failure_suite.py`: **4 passed**.
- `python scripts/benchmark_risk_gate.py`: **PASS**.
- В синтетическом Risk Engine benchmark 40/40 угроз по-прежнему направляются в AI; ни одна синтетическая угроза не обходит AI gate.
- Новый unit-тест подтверждает, что несколько писем помещаются в один HTTP-запрос и результаты сопоставляются по ID даже при обратном порядке ответа модели.
- Тестирование worker подтверждает, что в одном пакете FAST-письма не попадают в AI-запрос, а AI-кандидаты классифицируются общим вызовом.

## Что нельзя утверждать без live-теста

В текущей среде не использовался рабочий ключ DeepSeek, поэтому я не запускал внешнюю 70-писемную классификацию через реальный API. По этой причине пока не измерены:

- средняя и p95 latency пакетного запроса DeepSeek;
- фактическое время от приёма SMTP до готовности решения;
- реальное число HTTP-запросов DeepSeek на внешнем QA-наборе;
- exact-match качество новой пакетной классификации на всех 70 примерах.

Пакетирование в первую очередь уменьшает число HTTP round-trips и улучшает агрегатную пропускную способность при плотном потоке. Оно **не гарантирует latency меньше 1 секунды для одного письма**: результат по-прежнему ждёт ответа модели, а сбор неполного пакета добавляет максимум 250 мс после первого задания. При низком потоке запрос из одного письма идёт старым одиночным путём.

## Проверка на машине разработчика

После установки рабочей конфигурации `.env`:

```powershell
docker compose up -d --build
python scripts/run_quality_suite.py --data test-data/external_qa_suite.json
```

Чтобы считать фактические HTTP-попытки и длительность запросов:

```powershell
docker compose logs --since=10m gateway | Select-String "DeepSeek HTTP request=|DeepSeek batch classified|DeepSeek unified classification|processed id="
```

Сравнить со старой версией стоит три величины на одном и том же наборе и окружении: общую wall time, среднее `processing_time_ms` и количество строк `DeepSeek HTTP request=`. Из-за разброса времени внешнего API желательно выполнить 3–5 прогонов.

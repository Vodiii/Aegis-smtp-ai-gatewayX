# Отчёт v0.8.12 — аудит логики метрик QA

## Что показал разбор результата v0.8.11

В пользовательском прогоне было: 70/70 по классификации/действию, SMTP submission 7.096 s, suite wall 21.861 s, сумма индивидуальных `processing_time_ms` 424.570 s, среднее 6065.3 ms, максимум 11498 ms. Эти значения сами по себе не противоречат друг другу: шлюз обрабатывает письма конкурентно, а в режиме batching несколько писем делят один и тот же сетевой запрос классификатора. Поэтому сумма длительностей по письмам — не wall-clock длительность теста.

В коде обнаружены два ограничения интерпретации: 

1. `processing_time_ms` начинается в `EmailProcessor.prepare()` после того, как worker забрал/собрал задания. Таймер заканчивается при завершении классификации и подготовке результата. Он **не включает** время ожидания до запуска worker и последующую SMTP-доставку; при batching он включает общее время пакетного AI-запроса для каждого письма в пакете.
2. Старая QA-петля прекращала ожидание сразу после появления всех строк `/api/messages`. Запись классификации сохраняется до отправки получателям, поэтому успешная таблица PASS не доказывала, что оригиналы и alerts уже доставлены.

## Изменения v0.8.12

- Теперь обычный QA ждёт, пока каждое сообщение получит конечный статус доставки, соответствующий **фактическому действию** шлюза. Параметр `--classification-only` отключает ожидание доставки для узкого теста классификации.
- Итоговый PASS проверяет ожидаемые категорию, действие и доставку. Для ожидаемого `DELIVER` требуется `ORIGINAL_SENT`, для `DELIVER_AND_ALERT` — `ORIGINAL_AND_ALERT_SENT`. Статусы отказа/неподтверждённой доставки приводят к FAIL.
- `suite end-to-end wall time` фиксируется при завершении ожидания, до печати 70 строк таблицы. При обычном режиме он покрывает отправку, ожидание результата классификации и подтверждение доставки по API.
- В отчёте отдельно показываются: SMTP submission time; полный wall-clock теста; интервал worker-классификации по временным меткам; сумма перекрывающихся длительностей по письмам; среднее, p50, p95, минимум и максимум.
- Времена не следует складывать между собой: это разные метрики с разной областью измерения.

- Реальный внешний QA с DeepSeek после изменения отчётных метрик не запускался в данной среде; требуется запустить на системе пользователя.

## Следующий запуск

Обычный end-to-end QA, включая подтверждение доставки:

```powershell
python scripts/run_quality_suite.py --data test-data/external_qa_suite.json
```

Только категория/действие без ожидания физической доставки:

```powershell
python scripts/run_quality_suite.py --data test-data/external_qa_suite.json --classification-only
```
